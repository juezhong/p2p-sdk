# 开发路线（草案 v0.3）

所有下述功能均为待开发，完成情况以测试、代码与验收记录为准。

## M0 — 工程基线与安全约束
- Rust Cargo crate、CI、rustfmt、clippy、测试与示例。
- 明确 SDK API 规划、错误模型、取消/超时规则与身份模型。
- 确定协议兼容性策略；审查旧 Go `p2p-friend` 代码和许可证。
**完成条件**：跨平台构建验证计划成型，基础代码检查通过。

## M1 — ICE/Quinn UDP I/O 原型（首个关键风险）
- 比较 `is`、`webrtc-ice` 的维护状态、API 及候选处理能力。
- 实现基础 host/STUN 地址发现与两机候选检查。
- 验证 ICE STUN 流量与 Quinn QUIC 流量使用一致的 UDP 映射：Socket 移交或统一收发分发。
- 一条验证成功的 ICE 路径可继续完成 QUIC TLS 对端认证握手及 Stream echo。
**完成条件**：双机真实网络直连，不依赖中继；有可复现日志与网络抓包证据。若现有库难以集成，允许调整选型，不接受伪造成功状态。

## M2 — IPv6/IPv4/端口映射与失败处理
- 双栈候选检查、IPv6 优先、IPv4 可用性 fallback、LAN。
- IPv4 NAT 打洞、prflx 地址、可选 PCP/NAT-PMP/UPnP 显式映射。
- 严格 Direct-only、超时取消、资源回收、路径失败原因。
**完成条件**：docs/TESTING.md 的核心网络矩阵通过且不存在无意业务中继。

## M3 — 手动与自动两套信令
- 一次性邀请码/回传码、能力与会话认证、格式版本。
- 纯信令 Rendezvous 客户端协议；Trickle ICE、授权和速率限制。
- 信令服务器可由后续独立仓库实现；不将其设为离线手动模式强依赖。
**完成条件**：手动模式断开信令服务器仍可工作；自动模式只通过服务器交换控制信息。

## M4 — SDK API、诊断与多应用集成
- 稳定 Session、Stream、Datagram（条件启用）、事件和诊断 API。
- 脱敏 JSON 诊断输出；网络切换与重连恢复实验。
- 集成到 Rust `p2p-transfer`，然后供 `p2p-tunnel`、`p2p-net` 消费。
**完成条件**：应用无自实现 NAT 穿透状态机；可用文档和示例调用。

## 暂不实现

TCP ICE、TURN/Relay、多节点 Mesh、完整 VPN、SSH 服务端、GUI 和文件协议都不属于 SDK 第一阶段任务。跨平台 UI 由应用仓库负责，应用必须交付 CLI/TUI/GUI。

## 改动管理

若试验推翻某项设计，先记录实证结果、影响范围和替代方案，再修订架构文档；禁止以“已实现”描述未经验证的功能。
