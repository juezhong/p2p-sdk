# 手动 INVITE/REPLY：无需消息服务器，也不额外让用户输入 Session Secret

> **实现阶段：M1 离线编码/密钥派生原型。尚未与 ICE 候选、真正的双向 Quinn TLS 指纹验证及用户比较码确认集成。不得用于未经验证的生产文件传输。**

## 用户操作

1. A 生成一次性 INVITE（默认有效期建议 10 分钟，最长 30 分钟），复制给 B。
2. B 粘贴 INVITE，生成 REPLY 交还 A。
3. A 输入 REPLY。双方各自算出同一个内部 Session Secret，**不发送秘密本身，也无需用户额外输入密钥**。
4. 双方通过可信的独立渠道核对 6 位比较码，核对成功之后才允许将两个 QUIC 连接标记为可信。对端实际出示的 TLS 证书 SHA-256 必须与连接码中的指纹一致。
5. 通过 ICE 直连、QUIC/TLS 验证后，Control QUIC 与 Data QUIC 通过共同 Session ID 和会话内密钥独立绑定。

消息服务器（后续可选）只负责传递这些配对元数据，并不产生不同的 P2P 安全协议或中继任何数据。**区别是用户交互与信令传递方式，而不是有无加密/认证**。

## 当前二进制代码（新 Rust 方案；与旧 Go P2PF 格式不兼容）

- INVITE：魔数、版本、16 字节随机会话 ID、到期时间、A 临时 X25519 公钥、A 的 TLS 证书指纹、随机数。
- REPLY：魔数、版本、对应会话 ID/到期时间、B 临时 X25519 公钥、B 的 TLS 证书指纹、随机数、完整 INVITE SHA-256 承诺。
- 编码：URL-safe Base64，无填充，固定长度及前缀。解析限长，检查协议版本、时间、会话 ID、指纹和答复对应的 INVITE。
- X25519 共享密钥通过 HKDF-SHA256 和完整 INVITE/REPLY transcript 派生两个独立输出：会话绑定密钥与 6 位人工比较码。
- 双方使用上述内部密钥进行当前 SDK 的 Control/Data 双向 HMAC-SHA256 Session 绑定。
- 临时 X25519 私钥状态由 `finish` 消费；同一次 INVITE 不应该再次使用。

**注意：6 位数字不具有防暴力枚举的密钥强度，也不能在发码和回复码同一个可能被攻击者控制的渠道里盲目相信“双方显示一致”。** 必须建立清晰的人为核对或可信设备指纹确认流程。密钥派生不是持久设备认证，TLS 真实证书校验不能跳过。当前传入的 32 字节 fingerprint 仅为声明，必须由未来 Quinn 层进行比对。

## 后续必须完成的工作

- 与 SDK 的真实 ICE 候选/ufrag/password 完整 OFFER/ANSWER 编码整合，并限制单条连接码大小/候选数量；当前格式不包含网络候选，因此无法仅凭此码连接两台机器。
- 真实设备/会话 TLS 证书 SHA-256 校验（两条 QUIC 同一对端身份，含会话轮换和过期策略）。
- 人工比较码确认的状态机：未确认不能开放业务数据；可选持久受信设备以指纹/密钥匹配代替重复确认。
- 会话撤销、过期、重放、防 DoS、并发配对、时间同步偏差和单次消费状态。
- 真实 LAN/IPv4/IPv6/ICE 双机连通性与安全审查。
